Q17. What causes a cold start, and how does it affect latency? A cold start happens when no warm environment is available, so Lambda must run the Init phase (spin up the microVM, load the runtime, run your init code) before invoking. This adds latency, from tens of ms to a few seconds depending on runtime and package size. Warm invocations skip it. Cold starts are most visible with spiky traffic, large packages, VPC-attached functions and heavy runtimes such as Java and .NET.

Q18. What is Provisioned Concurrency, and how does it remove cold starts? Provisioned Concurrency (PC) pre-initializes a set number of execution environments and keeps them warm, so invocations skip Init and get consistent low latency. You pay for the provisioned capacity whether it is used or not. It is often paired with Application Auto Scaling and used on a function alias or version.

Q19. What is Lambda SnapStart, and how does it work for Java? SnapStart (first for Java, now broader) snapshots the memory and disk of the initialized environment after Init, encrypts and caches it, and restores from that snapshot on invoke instead of re-running Init. It can cut Java cold starts sharply at no extra cost. Caveat: uniqueness. Anything created once at Init (random seeds, connection tokens) is captured in the snapshot, so use runtime hooks (afterRestore) to regenerate per-restore state.
