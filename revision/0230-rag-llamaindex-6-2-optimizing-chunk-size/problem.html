RAG with LlamaIndex › 6. Advanced RAG: Pre-Retrieval & Indexing › 6.2 Optimizing chunk size

Chunking commandment (Greg Kamradt): don't chunk for chunking's sake; get data into a form that can be retrieved for value later.

The lowest-hanging fruit: chunk size affects response time, faithfulness, and relevancy. LlamaIndex defaults: chunk size 1024 tokens, overlap 20.

Effect
Smaller chunks (e.g., 128)More precise, focused embeddings; granular but may lack context
Larger chunks (e.g., 512+)Broader context, good for overviews; may include irrelevant text, miss detail
OverlapShared tokens between neighbors preserve context across boundaries
Chunk size vs similarity_top_kSmaller chunks → raise similarity_top_k to compensate (halving 1024→512 means retrieve more chunks)

TokenTextSplitter splits by token count (tokenizer default cl100k_base); SentenceSplitter keeps sentences/paragraphs whole (NLTK Punkt), so chunk sizes vary.
