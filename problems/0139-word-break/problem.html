139. Word Break Medium String Dynamic Programming Memoization
Key idea: dp[i] = "can the first i letters be split into words?" with dp[0] = true. dp[i] is true if some word ends exactly at i and the part before it, dp[i - len], is true. Only the word lengths that exist in the dictionary need trying (at most 20).

Problem View on LeetCode (opens in a new tab) ↗

Return true if s can be split into one or more words from wordDict, with nothing left over. A word can be used any number of times.

  • 1 <= s.length <= 300
  • 1 <= wordDict.length <= 1000, each word 1 to 20 letters, all different
  • Lowercase English letters only

Example: "leetcode", ["leet","code"] → true. "catsandog", ["cats","dog","sand","and","cat"] → false.

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
"leetcode", ["leet","code"] true Leaving out dp[0] = true makes every dp[i] false: said false.
"catsandog", ["cats","dog","sand","and","cat"] false "cats" + "and" and "cat" + "sand" both reach "og", and neither can finish.
"applepenapple", ["apple","pen"] true A word can be used more than once.
"cars", ["car","ca","rs"] true Taking the longest word first ("car") leaves "s". Greedy fails; you have to try "ca" too.
"a" × 24 + "b", ["a","aa",…,"a"×10] false Many ways to split the a's, none can use the b. Plain recursion took 7.2 s in Python here. A memo that saves only the true answers is just as slow (7.9 s).
300 letters, 1000 words either The largest input. Both DP versions finish in a few milliseconds.

Approach 1: Plain Recursion

can(start): if start is the end of s, the split worked. Otherwise try every word that matches at start and ask can(start + len(word)).

  • Clearly right, and the starting point for the memo version.
  • The same start is reached by many different splits of the letters before it, and each time it's worked out from scratch.
Time O(2ⁿ) worst case Space O(n) call stack

On "a" × k + "b", the time grows about 4× every 2 letters. Python: 0.44 s at k = 20, 1.8 s at 22, 7.2 s at 24. C++: 3.6 s at 26, 14 s at 28. At 300 letters it would never finish.

Approach 2: Recursion With a Memo

The answer for can(start) depends only on start. Save it the first time, and return the saved answer every time after.

  • Save false answers too. They're the ones that repeat: a true ends the search right away.
  • At most n + 1 different starts, each trying every word once.
Time O(n · m · L) Space O(n)

m = number of words, L = longest word. At full size here (300 letters, up to 1000 words): Python 1.1–2.3 ms, Java 2.5–5.8 ms, C++ under 0.4 ms. The recursion is at most 300 deep, which is fine for Python.

Approach 3: Bottom-Up DP Over Word Lengths Optimal

Fill dp[i] from 1 to n. For each word length L in the dictionary, if dp[i - L] is true and s[i-L:i] is in the word set, then dp[i] is true. Return dp[n].

  • Try lengths, not words: there are at most 20 different lengths but up to 1000 words.
  • No recursion, and each dp[i] is filled once.
Time O(n · k · L) Space O(n + m · L)

k = number of different word lengths (≤ 20). At full size: Python 0.3 ms, Java 1–3 ms, C++ 0.16 ms, the fastest here. The expected answer; a trie of the words is another way to speed up the inner loop.

In practice No shortcut

A regex looks like one: re.fullmatch("(?:leet|code)*", s) gives the right answer here. But the regex engine backtracks just like Approach 1: on "a" × k + "b" it grew about 4× every 2 letters (0.17 s at k = 22).

Use Approach 3. In Python, functools.cache on Approach 1's can turns it into Approach 2 in one line.
