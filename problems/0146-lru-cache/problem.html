146. LRU Cache Medium Design Hash Table Linked List
Key idea: A hash map finds a key's entry in O(1); a doubly linked list keeps entries in order of use and moves or removes any of them in O(1). Store nodes in the map, keep the most recent right after a head sentinel, and evict the node just before tail. Each node stores its key so the evicted one can be removed from the map.

Problem View on LeetCode (opens in a new tab) ↗

Design a cache that holds at most capacity keys. get(key) returns the value, or -1 if it's missing. put(key, value) adds or updates a key; if that makes the cache too big, it removes the least recently used key. Both count as a use. Both must run in O(1) on average.

  • 1 <= capacity <= 3000
  • 0 <= key <= 10⁴, 0 <= value <= 10⁵
  • At most 2 × 10⁵ calls to get and put

Example, capacity 2: put(1,1), put(2,2), get(1) → 1, put(3,3) evicts 2, get(2) → -1, put(4,4) evicts 1, get(1) → -1, get(3) → 3, get(4) → 4.

Approach 1: List in Order of Use

Keep [key, value] pairs in a list, least recently used first. To use a key, find it, remove it and append it at the back. To evict, remove the front.

  • Easy to see that it's right.
  • Finding a key and removing from the middle both scan the list: O(capacity) per call.
Time O(capacity) per call Space O(capacity)

2 × 10⁵ calls with capacity 3000 here: Python 11–16 s, Java 0.4–0.7 s, C++ 0.17–0.22 s. Fails the O(1) requirement.

Approach 2: Timestamps and a Lazy Heap

Each use gets a new time from a counter. A hash map holds each key's value and latest time; a min-heap holds (time, key). To evict, pop from the heap until an entry's time matches its key's current time: older entries are skipped.

  • A key's older entries always have smaller times, so they're popped and skipped before its current one. An evicted key never leaves an entry behind.
  • Old entries are only cleared on eviction. With one key and 199,999 get calls, the heap held 200,000 entries.
Time O(log n) per call (amortized) Space O(number of calls) worst case

n = heap size. Fast in practice: Python 140–180 ms, Java 64–74 ms, C++ 40–43 ms on the 2 × 10⁵-call tests. Not O(1), and its memory isn't bounded by the capacity.

Approach 3: Hash Map + Doubly Linked List Optimal

The map gives a key's node. The list is ordered by use, most recent right after head. get: unlink the node and put it after head. put: update and move an existing node; otherwise, if full, remove tail.prev from the list and the map, then add a new node after head.

  • Doubly linked: removing a node needs its prev, and the map can't give that.
  • Sentinel head and tail nodes mean the list is never empty, so there are no null checks.
  • Check "already there?" before "full?": an update never evicts.
Time O(1) per call Space O(capacity)

Python 73–75 ms, Java 34–39 ms, C++ 25–32 ms on the 2 × 10⁵-call tests. The expected answer, and the classic "design" interview question.

In practice Built-ins

Python's OrderedDict has move_to_end and popitem(last=False). Java's LinkedHashMap with accessOrder = true and removeEldestEntry is an LRU cache already. C++'s std::list is a doubly linked list, and splice moves a node in O(1).

Time O(1) per call Space O(capacity)

Python 50 ms (the fastest Python version here), Java 34 ms, C++ 25–33 ms. What you'd use in real code; in an interview, expect to build Approach 3 yourself. (Python's functools.lru_cache caches a function's results, not a key–value store.)
