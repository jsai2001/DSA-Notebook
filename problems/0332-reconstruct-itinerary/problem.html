332. Reconstruct Itinerary Hard Graph Eulerian Path DFS
Key idea: Using every ticket once is an Eulerian path. Hierholzer: from JFK, keep flying the smallest ticket left. When an airport has no tickets left, it goes on the route. The route comes out backwards, so reverse it. A dead end can only be the true end, so no backing up is needed. O(E log E) for the sort.

Problem View on LeetCode (opens in a new tab) ↗

Each ticket is [from, to]. Start at "JFK" and use every ticket exactly once. If more than one route works, return the smallest one in dictionary order (compare airport by airport). At least one route always exists.

  • 1 <= tickets.length <= 300, airports are 3 capital letters, from != to

Example: [["MUC","LHR"],["JFK","MUC"],["SFO","SJC"],["LHR","SFO"]] → ["JFK","MUC","LHR","SFO","SJC"]. [["JFK","SFO"],["JFK","ATL"],["SFO","ATL"],["ATL","JFK"],["ATL","SFO"]] → ["JFK","ATL","JFK","SFO","ATL","SFO"].

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
[["JFK","KUL"],["JFK","NRT"],["NRT","JFK"]] ["JFK","NRT","JFK","KUL"] KUL is smaller, but flying there first gets stuck with tickets left. Always taking the smallest, with no backing up and no Hierholzer, gives ["JFK","KUL"]. That bug was wrong on 522 of 1,908 tests.
[["JFK","AAA"],["AAA","JFK"],["JFK","AAA"],["AAA","JFK"]] ["JFK","AAA","JFK","AAA","JFK"] The same ticket can appear more than once. Keep a list, not a set.
300 tickets 301 airports in the route The recursive versions can go about 300 calls deep. That's fine in all three languages (Python's default limit is 1,000); the Python files raise the limit anyway.

Approach 1: Backtracking

Sort the tickets. From the current airport, try its unused tickets smallest first. If the route gets stuck before every ticket is used, undo the last ticket and try the next one. The first full route found is the smallest.

  • Skip a ticket equal to one just tried from the same airport: it would lead to the same dead end.
  • Easy to get right. It just does extra work at dead ends.
Time O(E log E) plus the work undone at dead ends Space O(E)

300 random tickets over 4 airports: Python 0.86 ms, C++ 0.33 ms, Java 0.25 ms, 4 to 6 times the time of Approach 3. Still fast at LeetCode's size.

Approach 2: Hierholzer, Recursive

visit(a): while a has a ticket left, fly the smallest one and visit there. When none are left, add a to the route. A place you get stuck early (like KUL above) gets added first, so it ends up last after the reverse. Everything else gets spliced in before it.

  • Sort each airport's list biggest first, so pop() from the end gives the smallest in O(1).
  • Every ticket is flown once. No undo.
Time O(E log E) Space O(E)

300 tickets, 4 airports: Python 0.21 ms, C++ 0.064 ms, Java 0.055 ms. Within noise of Approach 3.

Approach 3: Hierholzer With a Stack Optimal

The same idea as Approach 2 without recursion. The stack is the current path. If the top airport has a ticket left, push its smallest destination. If not, pop it onto the route. Reverse at the end.

  • No recursion limit to worry about.
Time O(E log E) Space O(E)

300 tickets, 4 airports: Python 0.16 ms, C++ 0.059 ms, Java 0.055 ms. Approaches 2 and 3 swapped places on other inputs, so treat them as the same speed.

In practice No shortcut

Nothing built in. Approach 3 is what you'd write.
