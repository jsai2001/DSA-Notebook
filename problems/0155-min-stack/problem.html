155. Min Stack Medium Stack Design
Key idea: The minimum only changes when a value is pushed or popped at the top, so remember it per level. Either store (value, minimum at or below) in each entry, or keep a second stack of minimums and push to it when a value is ≤ its top. Everything is O(1).

Problem View on LeetCode (opens in a new tab) ↗

Design a stack with push(val), pop(), top() and getMin(), which returns the smallest value on the stack. Each must run in O(1).

  • -2³¹ <= val <= 2³¹ - 1
  • pop, top and getMin are only called on a non-empty stack
  • At most 3 × 10⁴ calls

Example: push(-2), push(0), push(-3), getMin() → -3, pop(), top() → 0, getMin() → -2.

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
push 0, push 1, push 0, getMin, pop, getMin 0, 0 The minimum is pushed twice. Adding to the min stack only on a strictly smaller value lost it after one pop: IndexError on the second getMin.
push 1000, push 500, pop, getMin 1000 Java: comparing two Integers with == compares objects. It said 500 here, but gave the right answer for small values like 50 and 100, so it passes easy tests. Use .equals.
push 2³¹ − 1, push −2³¹, getMin, pop, getMin -2147483648, 2147483647 The full int range. Tricks that store "value minus minimum" overflow here.
15,000 pushes, then 15,000 getMin - Scanning on each getMin is 2.25 × 10⁸ reads: 4.8 s in Python here.

Approach 1: Scan on getMin

A plain stack. getMin looks at every value and returns the smallest.

  • push, pop and top are O(1); only getMin is slow.
  • Fails the O(1) requirement.
Time getMin O(n), the rest O(1) Space O(n)

15,000 pushes then 15,000 getMin: Python 4.8 s, Java 0.19 s, C++ 12 ms.

Approach 2: Store the Minimum With Each Entry

Push (val, min(val, minimum of the entry below)). The top entry's second number is always the current minimum. Popping reveals an entry that already knows its own minimum.

  • The simplest O(1) design: nothing to keep in sync.
  • Always stores two numbers per value.
Time O(1) per call Space O(n), 2 numbers per entry

Same big run: Python 6 ms, Java 13 ms, C++ 2.3 ms, about 800× faster than Approach 1 in Python.

Approach 3: A Second Stack of Minimums Optimal

Keep all values on stack. On push, also push onto mins if the value is ≤ the top of mins. On pop, if the popped value equals the top of mins, pop that too. getMin is the top of mins.

  • ≤ keeps a copy for every repeat of the minimum, so popping one copy leaves the others.
  • mins is usually small: 13 entries for 15,000 random pushes here. Its worst case is a decreasing sequence, where it holds every value (15,000 of 15,000).
Time O(1) per call Space O(n) worst, usually much less

Same big run: Python 5 ms, Java 10 ms, C++ 2.3 ms. The usual answer, with the ≤ and (in Java) the .equals as the two details to get right.

In practice No shortcut

No standard stack tracks its minimum. A heap gives the minimum, but it can't remove the most recently pushed value, so it doesn't fit.

Approach 2 or 3 is what you'd write. Approach 2 is harder to get wrong; Approach 3 saves memory when minimums change rarely.
