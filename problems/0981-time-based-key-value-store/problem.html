981. Time Based Key-Value Store Medium Binary Search Design Hash Map
Key idea: set timestamps only go up, so appending (time, value) to each key's list keeps it sorted for free. A get is then a binary search for the last time <= timestamp: find the first time that's bigger and step back one. O(1) set, O(log n) get.

Problem View on LeetCode (opens in a new tab) ↗

Build a TimeMap:

  • set(key, value, timestamp) stores value for key at that time.
  • get(key, timestamp) returns the value set with the largest time <= timestamp, or "" if there is none.
  • The timestamps of set calls strictly increase. 1 <= timestamp <= 10⁷, at most 2·10⁵ calls.

Example: set("foo","bar",1), get("foo",1) → "bar", get("foo",3) → "bar", set("foo","bar2",4), get("foo",4) → "bar2", get("foo",5) → "bar2".

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
set("b","cbc",3), get("b",3) "cbc" An exact time match counts. bisect_left instead of bisect_right skipped it and returned "": wrong on 346 of 1,503 tests.
set("a","x",5), get("a",4) "" Every stored time is later than the query.
get("zz",5) before any set of "zz" "" An unknown key must not crash.

Approach 1: Try Every Earlier Time

Store each value under (key, timestamp). For a get, look up timestamp, then timestamp − 1, and so on down to 1.

  • A get long after the last set, or for an unknown key, tries up to 10⁷ times.
Time set O(1), get O(timestamp) Space O(n)

1,000 gets that each try 10⁴ times: Python 0.46 s, Java 0.22 s, C++ 0.27 s. One get at time 10⁷ is 1,000 times that work.

Approach 2: Sorted List per Key, Scan Back

Append (time, value) to the key's list; it stays sorted. For a get, walk back from the newest pair and return the first one at or before timestamp.

  • Fast when queries ask about recent times. Slow when they ask about old ones.
Time set O(1), get O(pairs for that key) Space O(n)

2·10⁵ random calls on 10 keys: Python 1.6 s, Java 66 ms, C++ 21 ms. One key with 2·10⁴ pairs and 2·10⁴ gets for early times: Python 12 s. But for recent times it beat Approach 3 in Python (57 ms vs 161 ms).

Approach 3: Sorted List per Key, Binary Search Optimal

Same lists. For a get, binary search for the first pair whose time is greater than timestamp. The pair just before it is the answer; if there's none before it, return "".

  • Searching for "first time > t" handles exact matches without a special case.
Time set O(1), get O(log n) Space O(n)

2·10⁵ random calls: Python 146 ms, Java 25 ms, C++ 9.6 ms. The early gets that took Approach 2 twelve seconds: Python 28 ms, Java 2.3 ms, C++ 1.5 ms.

In practice Built-ins

Python: bisect_right on a list of times. C++: a std::map per key with upper_bound. Java: a TreeMap per key with floorEntry.

Time set O(1) / O(log n), get O(log n) Space O(n)

Should pass on LeetCode. 2·10⁵ random calls: Python 62 ms, 2.3 times faster than Approach 3 (the search runs in C). The tree maps were slower than Approach 3: C++ 17 ms, Java 35 ms.
