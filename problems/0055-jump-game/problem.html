55. Jump Game Medium Array Greedy Dynamic Programming
Key idea: The reachable indices are always one block starting at 0, so one number describes them: farthest. Scan left to right; if i > farthest, you're stuck and the answer is false. Otherwise farthest = max(farthest, i + nums[i]). Check before you update. O(n) time, O(1) space.

Problem View on LeetCode (opens in a new tab) ↗

You start at index 0 of nums. Each nums[i] is your maximum jump length from index i: you can jump to any index from i + 1 up to i + nums[i]. Return true if you can reach the last index, otherwise false.

  • 1 <= nums.length <= 10⁴ and 0 <= nums[i] <= 10⁵.

Examples: [2,3,1,1,4] → true (0 → 1 → 4); [3,2,1,0,4] → false (every path ends on the 0 at index 3).

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
[0] true You start on the last index, so no jump is needed. The 0 doesn't matter.
[0,1] false Stuck at the start. Updating farthest with index 1 before checking i > farthest lets the unreachable index vouch for itself and returns true.
[1,0] true A 0 on the last index is fine: you never jump from there.
[3,2,1,0,4] false Every index before the 0 reaches exactly index 3 and no further. Big numbers early on don't help if they all stop at the same wall.
[2,3,1,1,4] true From 0 you can land on 1 instead of jumping the full 2. Moving the goal only when i + nums[i] > goal (not >=) misses exact landings and returns false.
[2,0,0] true Jump straight over the 0 in the middle onto the last index.
[1,1,0,1] false The 0 isn't at the start: you walk into it, and nothing earlier jumps over it.
10⁴ values of 10⁵ true Jumps go far past the end; you only need to reach the last index. i + nums[i] is at most about 1.1 × 10⁵, so int is fine.

Approach 1: Dynamic Programming

Call an index good if the last index can be reached from it. The last index is good. Going right to left, i is good if any index it can jump to is good. The answer is good[0].

  • Stop scanning i's range at the first good index: one is enough.
  • Going right to left matters: every good[j] with j > i is already known when i needs it.
Time O(n · k), k = max(nums) Space O(n)

Easy to trust, but slow on long runs of bad indices. On an input built for it ([5000, 4999, …, 1] followed by 5000 zeros, so every index scans its whole range and finds nothing) it took 0.26 s in Python here, 14 ms in C++. Most inputs finish in a couple of milliseconds, because the scan stops at the first good index.

Approach 2: Greedy, Move the Goal Left

Approach 1 only ever needs the leftmost good index so far. Call it goal, starting at the last index. Going right to left, if i + nums[i] >= goal, then i can land on goal, so reaching i is enough: goal = i.

  • The answer is goal == 0.
  • Use >=: landing exactly on goal is a valid jump.
  • Why only the leftmost one? If i can reach any good index, it can also reach the leftmost good index after it, since jumps can be any length up to nums[i].
Time O(n) Space O(1)

Approach 1 with the array squeezed down to one number. It always scans all n indices, even when the answer is clear early on.

Approach 3: Greedy, Farthest Reach Optimal

Go the other way. If you can reach index i, you can reach everything up to i + nums[i], so the reachable indices are always 0..farthest. Walk left to right: if i is past farthest, nothing can get there.

  • Check i > farthest first, then update farthest: only a reachable index may extend the reach.
  • If the loop finishes, every index was reachable, including the last.
Time O(n) Space O(1)

The expected answer, and the same "how far can I get" idea as Jump Game II (45), which counts the jumps as well. It stops as soon as it gets stuck.

In practice No shortcut

No standard library function solves this. A graph search over the jumps would work, but each index can have up to 10⁵ jumps, which is more work than Approach 1.

Write Approach 3: one variable, and check i > farthest before updating it.
