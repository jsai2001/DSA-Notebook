128. Longest Consecutive Sequence Medium Array Hash Table Sorting
Key idea: Put the numbers in a set. Only start counting at a number x whose x - 1 is not in the set: that's the first number of a run. Walk up x + 1, x + 2, … from there. Every number is walked once, so it's O(n).

Problem View on LeetCode (opens in a new tab) ↗

Given an unsorted array nums, return the length of the longest run of consecutive values (like 1, 2, 3, 4), in any order in the array. The problem asks for O(n) time.

  • 0 <= nums.length <= 10⁵
  • -10⁹ <= nums[i] <= 10⁹

Example: [100, 4, 200, 1, 3, 2] → 4 (1, 2, 3, 4). [0, 3, 7, 2, 5, 8, 4, 6, 0, 1] → 9.

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
[] 0 Empty input is allowed: no run at all, not 1.
[1, 2, 0, 1] 3 A repeat inside a run. After sorting (0, 1, 1, 2), treating the second 1 as a break says 2.
[1, 2, 3] 3 The longest run is at the very end. Updating the best only when a run breaks never counts it: said 0.
[5, 5, 5] 1 All the same: a run of one value.
[-1, 0, 1] 3 Runs can cross zero.
[1000000000, -1000000000] 1 The extremes: x + 1 and x - 1 still fit in a 32-bit int.
1 to 10⁵, shuffled 100000 One long run. Walking up from every number is about 5 × 10⁹ lookups.
1 to 8,000, plus 8,000 more 1s 8000 Many copies of a run's start. Looping over nums instead of the set walks the run once per copy: 7.5 s instead of 3 ms in Python here.

Approach 1: Walk Up From Every Number

Put the numbers in a set. From each number x, count how many of x + 1, x + 2, … are in the set, and keep the longest count.

  • Right, but wasteful: in a run of length m, each of its m numbers walks the rest of the run again.
  • One long run of n numbers costs about n² / 2 lookups.
Time O(n²) Space O(n)

Measured on one shuffled run, the time roughly quadruples each time n doubles. Python: 0.34 s at 2,000, 1.2 s at 4,000, 3.2 s at 8,000. C++: 0.17 s at 10,000, 0.85 s at 20,000, 5.3 s at 40,000. At n = 10⁵ that grows to roughly half a minute in C++ and several minutes in Python (estimated, not run).

Approach 2: Sort, Then Scan

After sorting, every run sits side by side. Scan once: a step of exactly +1 grows the current run, an equal value changes nothing, and anything bigger starts a new run.

  • Skip repeats; don't reset the run on them.
  • Update the best after every step, so the last run counts too.
  • C++ and Java sort the input in place. Copy it first if the caller still needs the original order.
Time O(n log n) Space O(1) extra (O(n) in Python's sorted)

Doesn't meet the O(n) rule, but it's fast in practice. At n = 10⁵ here: C++ 4.9 ms and Java 71 ms, both faster than the hash set in Approach 3. Python 73 ms. Worth mentioning in an interview as the simple option.

Approach 3: Start Only at a Run's First Number Optimal

Same set as Approach 1, but only walk up from x when x - 1 is not in the set. Any other number is inside a run that its first number will count.

  • Each number is checked once (is x - 1 there?) and walked over at most once, so at most about 2n lookups.
  • Loop over the set, not nums: with many copies of a run's first number, looping over nums walks the run once per copy and is O(n²) again.
Time O(n) Space O(n)

The answer the problem asks for. At n = 10⁵ here: Python 34 ms (2× faster than sorting), C++ 9.5 ms, Java 122 ms. O(n) doesn't mean faster everywhere: in C++ and Java, hashing every number cost more than sorting. Java also boxes each int into an Integer.

In practice Built-ins

Remove repeats and sort, then measure each run: sorted(set(nums)) with itertools.groupby in Python (inside a run, value minus position stays the same), std::sort + std::unique in C++, IntStream.distinct().sorted() in Java.

Time O(n log n) Space O(n)

Short and fast enough: Python 54 ms, C++ 5.8 ms, Java 310 ms (the stream has setup cost) at n = 10⁵ here. It's Approach 2 in fewer lines, so it doesn't meet the O(n) rule. In an interview, expect to be asked for Approach 3.
