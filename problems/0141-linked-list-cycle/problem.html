141. Linked List Cycle Easy Linked List Two Pointers Hash Table
Key idea: Two pointers: slow moves one node at a time, fast moves two. Without a cycle, fast reaches the end. With one, both end up going around it, fast gains one node per step, and they meet. O(n) time, O(1) memory.

Problem View on LeetCode (opens in a new tab) ↗

Given the head of a linked list, return true if some node can be reached again by following next, that is, if the list has a cycle. The tests describe the cycle with pos, the index the tail links back to (-1 = no cycle), but pos is not passed to your function.

  • 0 to 10⁴ nodes; -10⁵ <= Node.val <= 10⁵
  • Follow-up: can you do it with O(1) memory?

Example: [3,2,0,-4], pos = 1 → true (the tail links back to node 1). [1], pos = -1 → false.

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
[] false head is null. A loop that checks only fast.next crashed here (AttributeError); check fast first.
[1,2], pos = -1 false Even length: fast jumps past the last node to null. Checking only fast.next crashed here too.
[1,2,1], pos = -1 false Values repeat. A set of values said true; store the nodes.
[1], pos = 0 true One node pointing to itself: the smallest cycle.
[1,2], pos = 0 true The whole list is the cycle.
10⁴ nodes, the tail pointing to itself true A long walk to a tiny cycle. Floyd made 29,997 pointer moves here, Brent 16,384.

Approach 1: Remember the Nodes

Walk the list and put each node in a hash set. If a node is already in the set, you've come back to it: a cycle. If you reach null, there is none.

  • Store the node itself (its identity), not its value: different nodes can hold the same value.
  • Easy to write, but the set grows with the list.
Time O(n) Space O(n)

At 10⁴ nodes here: Python 0.5 ms, Java 2.5–2.9 ms, C++ 0.6 ms (the slowest version in C++, because of the hashing). Doesn't meet the O(1)-memory follow-up.

Approach 2: Brent's Method

Keep anchor still and walk runner ahead in rounds of 1, 2, 4, 8, … steps. If runner lands on anchor, it went around a cycle. After each round, anchor jumps to where runner is.

  • Once a round is longer than the cycle, and anchor is inside it, runner comes back to anchor within that round.
  • Only one pointer walks the list, so it makes fewer moves than Floyd: 16,384 vs 29,997 on 10⁴ nodes with a self-loop at the tail, and 10,000 vs 15,000 with no cycle.
Time O(n) Space O(1)

Fewer moves didn't mean faster in Python (0.6–1.3 ms vs Floyd's 0.2–0.4 ms): each step does more bookkeeping. C++ 0.01–0.03 ms, Java 0.5–0.8 ms. Good to know when following next is expensive.

Approach 3: Slow and Fast Pointers (Floyd) Optimal

Move slow one step and fast two steps each round. If fast (or fast.next) is null, the list ends. If they ever point to the same node, there's a cycle.

  • Why they must meet: inside the cycle, the gap between them shrinks by exactly one node per round, so it can't skip past zero.
  • Loop while fast and fast.next: both are needed for the two-step move.
Time O(n) Space O(1)

At 10⁴ nodes: Python 0.2–0.4 ms, Java 0.4–0.5 ms, C++ 0.01–0.02 ms, the fastest here in every language. The expected answer. The same two pointers also find where the cycle starts (Linked List Cycle II).

In practice No shortcut

No standard library function checks a linked list for a cycle. A set (set, unordered_set, HashSet) is the only built-in that helps, as in Approach 1.

Approach 3 is what you'd write: five lines and no extra memory.
