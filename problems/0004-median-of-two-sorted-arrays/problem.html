4. Median of Two Sorted Arrays Hard Array Binary Search Divide and Conquer
Key idea: You don't need to merge. Binary search a cut in the shorter array so the left halves of both arrays hold exactly half of all elements, and every left value is <= every right value. The median then comes from the four values around the cut. O(log(min(m, n))).

Problem View on LeetCode (opens in a new tab) ↗

Given two sorted arrays nums1 (size m) and nums2 (size n), return the median of the two arrays combined. The overall run time should be O(log(m + n)).

  • 0 <= m, n <= 1000 and 1 <= m + n <= 2000
  • -10^6 <= nums1[i], nums2[i] <= 10^6
  • Median: the middle value if the total count is odd, otherwise the average of the two middle values.

Examples: [1,3] and [2] → 2.0 (merged [1,2,3]); [1,2] and [3,4] → 2.5 (merged [1,2,3,4]).

Approach 1: Merge, Then Pick the Middle

Merge the two sorted arrays with two pointers (the merge step of merge sort), then read the median from the middle of the merged list.

  • While both arrays have elements left, append the smaller one. On a tie, both are appended.
  • When one array runs out, append the rest of the other one.
  • Odd length: result[mid]. Even length: the average of result[mid - 1] and result[mid].
Time O(m + n) Space O(m + n)

Simple and correct, but it misses the required O(log(m + n)). A few small cleanups: the size-1 and size-0 special cases aren't needed (the general code already handles size 1, and the constraints guarantee at least one element). The size-1 shortcut also returns an int instead of a float; the value is still right. Also, import math is unused, and a conditional expression used only for its side effect (a.extend(x) if c else a.extend(y)) reads better as a plain if / else, which is how it's written below.

Approach 2: Two Pointers Without Storing

The median only depends on the elements at positions (m + n) / 2 - 1 and (m + n) / 2 of the merged order. So walk the merge without building the list, and just remember the last two values seen.

  • Step (m + n) / 2 + 1 times, each time taking the smaller front element (or whichever array still has elements).
  • Keep prev and curr. At the end, curr is the middle element; for even totals the median is (prev + curr) / 2.
Time O(m + n) Space O(1)

Same time as merging (about half the steps), but no extra array. A good stepping stone, and a fine answer if the interviewer doesn't insist on logarithmic time.

Approach 3: Binary Search on the Partition Optimal

Cut nums1 at i and nums2 at j so the left side has half = (m + n + 1) / 2 elements in total, which forces j = half - i. The cut is correct when every left value is <= every right value.

  • Binary search i over the shorter array (swap so nums1 is shorter). This keeps j in range.
  • Let L1 = nums1[i-1], R1 = nums1[i], L2 = nums2[j-1], R2 = nums2[j]. Use −∞ / +∞ when a cut is at an edge.
  • If L1 > R2, the cut in nums1 is too far right: move hi = i - 1. If L2 > R1, it's too far left: move lo = i + 1.
  • Once valid: odd total → max(L1, L2); even total → (max(L1, L2) + min(R1, R2)) / 2.
Time O(log(min(m, n))) Space O(1)

Meets the required O(log(m + n)), and is even better because it only searches the shorter array. The tricky parts are the edge sentinels and remembering to swap the arrays first.

In practice Built-ins

Combine the arrays and let the standard library find the middle: statistics.median in Python, a sorted IntStream in Java, and std::merge in C++.

Time O((m + n) log(m + n)) Space O(m + n)

Should pass on LeetCode (at most 2000 elements), but none of these meet the required O(log(m + n)). Python and Java sort the combined array, which hides an O(n log n) cost. C++'s std::merge uses the fact that both inputs are already sorted, so it's O(m + n): the same linear merge as Approach 1.
