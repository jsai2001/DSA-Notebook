23. Merge k Sorted Lists Hard Linked List Heap (Priority Queue) Divide and Conquer
Key idea: Never compare against all k heads one by one. Either keep the heads in a min-heap (pop the smallest, push its next node), or merge in pairs like merge sort (k lists → k/2 → k/4 → … → 1) using Merge Two Sorted Lists. Both give O(N log k) for N nodes in total.

Problem View on LeetCode (opens in a new tab) ↗

You're given an array of k linked lists, each sorted in ascending order. Merge them all into one sorted linked list and return it.

  • 0 <= k <= 10⁴ and each list has 0 to 500 nodes.
  • At most 10⁴ nodes in total (call it N).
  • -10⁴ <= Node.val <= 10⁴, and every list is sorted.

Examples: [[1,4,5],[1,3,4],[2,6]] → [1,1,2,3,4,4,5,6]; [] → []; [[]] → [].

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
[] [] No lists at all (k = 0): reading lists[0] is out of range.
[[]] [] One list, and it's empty: lists[0] exists but is null.
[[1,2,3],[],[],[4]] [1,2,3,4] Empty lists in the middle: a heap must skip null heads, or comparing .val crashes.
[[1,4,5],[1,3,4],[2,6]] [1,1,2,3,4,4,5,6] The usual case, with equal values in different lists.
[[5,6],[1,2],[3,4]] [1,2,3,4,5,6] The head of the answer doesn't come from lists[0]. A dummy node avoids picking the head up front.
[[2,2],[2],[2,2,2]] [2,2,2,2,2,2] All ties. In Python 3, a heap of (val, node) tuples compares the nodes on a tie and raises TypeError: add the list index as a tie-breaker.
[[-10000,0,10000],[-10000],[10000]] [-10000,-10000,0,10000,10000] The extreme values: don't start a "smallest so far" at 0 or use a sentinel inside the range.
10⁴ lists of 1 node each 10⁴ nodes The case that sinks merging one list at a time: about 5 × 10⁷ node steps. It took 1.6 s in Python here (3.2 s with all values equal), where the heap took 0.01 s.
One list of 10⁴ nodes + 9,999 empty lists The long list k is huge but almost every list is empty: the answer should cost about N, not k · N.

Approach 1: Collect, Sort, Relink

Ignore that the lists are sorted: put all N nodes in one array, sort it by value, and link the nodes in that order.

  • It reuses the same nodes, so nothing new is allocated (and nothing leaks in C++).
  • Remember to set the last node's next to null.
Time O(N log N) Space O(N)

Simple and fast enough here (N ≤ 10⁴), but it wastes the sorted order and needs an array of every node.

Approach 2: Merge One List at a Time

You already know how to merge two lists (LeetCode 21). Merge the first list into an empty answer, then the second into that, and so on.

  • The catch: every merge walks the whole answer so far again. The nodes from the first list get walked about k times.
  • With k lists of about N / k nodes, that's about N / k · (1 + 2 + … + k) ≈ k · N / 2 steps.
Time O(k · N) Space O(1)

Fine for a few lists. At k = N = 10⁴ it's around 5 × 10⁷ steps: it passed here in C++ and Java (about 0.1 s), but took 1.6 to 3.2 s in Python, which risks Time Limit Exceeded.

Approach 3: Min-Heap of the Heads

The next node of the answer is always the smallest of the k current heads. A min-heap gives that smallest head in O(log k) instead of checking all k.

  • Push the head of every non-empty list.
  • Pop the smallest, attach it to tail, and push its next (if any). The heap never holds more than k nodes.
  • Python's heapq compares whole tuples, so push (val, i, node): the list index i settles ties before Python tries to compare two nodes. C++'s priority_queue puts the largest on top, so its comparator uses >.
Time O(N log k) Space O(k)

The answer most interviewers expect, and the idea behind merging many sorted files on disk (k-way merge). It also works when the lists are streams you can only read from the front.

Approach 4: Divide and Conquer (Merge in Pairs) Optimal

Do what merge sort does: merge the lists in pairs, then merge the results in pairs, until one list is left. Every round halves the number of lists, so there are about log₂ k rounds.

  • In one round each node is in at most one merge, so a round costs O(N). log k rounds give O(N log k).
  • Bottom-up with a step: merge lists[i] with lists[i + step] for i = 0, 2·step, 4·step, …, then double step. The answer ends up in lists[0].
  • No recursion and no heap, so the only extra memory is a few pointers.
Time O(N log k) Space O(1)

As fast as the heap with less memory, and it reuses the two-list merge you already have. It does overwrite entries of the input array, which is fine on LeetCode.

In practice No shortcut

There's no library call that merges LeetCode's ListNode lists. Python's heapq.merge and C++'s std::merge work on iterables and iterators, and would mean copying values out and building new nodes. What the library does give you is the heap: heapq, std::priority_queue and java.util.PriorityQueue.

Write Approach 3 or 4. The heap version is the one to know by heart: "the smallest of k candidates, again and again" is a heap problem.
