621. Task Scheduler Medium Greedy Heap (Priority Queue) Counting
Key idea: Only the most frequent task decides the length. If it appears most times, it needs most − 1 blocks of n + 1 units, plus a last block holding every task tied for most. Other tasks fill the gaps. If they overflow them, there's no idle at all. So the answer is max((most − 1)(n + 1) + tied, len(tasks)), O(N).

Problem View on LeetCode (opens in a new tab) ↗

tasks is a list of letters, each one unit of work. A CPU runs one task (or sits idle) per time unit, in any order, but two runs of the same letter must be at least n units apart. Return the fewest time units needed to run them all.

  • 1 <= tasks.length <= 10⁴; tasks are uppercase letters A–Z.
  • 0 <= n <= 100.

Examples: ["A","A","A","B","B","B"], n = 2 → 8 (A B idle A B idle A B); n = 3 → 10; ["A","C","A","B","D","B"], n = 1 → 6.

Edge cases

Try these against your solution before reading the approaches.

Input Expected Why it's tricky
"AAA", n = 0 3 No waiting: the answer is just the number of tasks.
"A", n = 5 1 Nothing comes after the last run, so no wait is needed there. Counting a full block for it gives 6.
"AAABBB", n = 2 8 A and B are tied for most: the last block has both. Forgetting the tie (adding 1) says 7.
"AABBCCDD", n = 1 8 More kinds than slots: no idle is needed. The formula alone gives 6, less than the 8 tasks; take the max with len(tasks).
"AAAAAABCDEFG", n = 2 16 Six A's need 5 blocks of 3 plus one A. The 6 other tasks fill 6 of the 10 gaps; 4 stay idle.
"BBBBA", n = 3, simulating 13 Running any allowed task (here A first, alphabetically) wastes the time B needs most: 14. Always run the one with the most left.
10⁴ × "A", n = 100 1009900 Almost all idle. A simulation goes through about 10⁶ time units (552 ms in Python); the formula doesn't care.

Approach 1: Simulate, Pick the Most Left

Run the clock one unit at a time. Each unit, among the letters allowed to run (their wait is over), run the one with the most copies left, and mark it as waiting until time + n + 1. If none is allowed, the unit is idle.

  • Most-left first matters: the most frequent task is the one most likely to cause idle later, so start it early.
Time O(T · 26), T = the answer Space O(1)

A direct picture of the rules, but it walks every idle unit too: 552 ms for 10⁴ A's with n = 100.

Approach 2: Max-Heap and a Waiting Queue

The same greedy, organised: a max-heap holds the counts of tasks ready to run, and a queue holds tasks that just ran, with the time they may run again. Each unit: run the top of the heap (if any); when the front of the queue is ready, move it back into the heap.

  • Tasks leave the queue in the order they entered, since they all wait the same n.
  • Python: store counts as negatives (min-heap). C++/Java: a max-heap directly.
Time O(T · log 26) ≈ O(T) Space O(26)

The answer most people give: 75 ms for the all-A case, and it still visits every idle unit.

Approach 3: Count the Blocks Optimal

Picture the most frequent task as a frame: most − 1 blocks of n + 1 units, each starting with it, then a last block with every task tied for most. Every other task fits in the gaps, since it has fewer copies than there are blocks.

  • frame = (most − 1) · (n + 1) + tied.
  • If there are more tasks than the frame holds, spread them out with no idle at all: the answer is len(tasks). So return max(frame, len(tasks)).
Time O(N) to count Space O(26)

No clock at all: 0.3 ms at the limit, whatever n is. Easy to get subtly wrong, so remember the two parts: tied and the max.

In practice No shortcut

Nothing schedules this for you, but counting is built in: collections.Counter in Python, or an array of 26 in C++ and Java. The heaps are heapq, std::priority_queue and PriorityQueue.

Write Approach 3 and explain it with the frame picture; mention Approach 2 when the real order of tasks is needed, not just the length.
